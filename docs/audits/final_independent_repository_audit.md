## 3. MPE complete audit

### 3.1 Shared-layer integrity
The shared extraction tests (`tests/test_shared_extraction.py`) explicitly guard against the architectural risks listed in the audit charter:
- `test_no_registry_or_protocol_id_branching` — no `protocol_id ==`, `PROTOCOL_REGISTRY`, or `HANDLERS` strings in shared modules.
- `test_pipeline_does_not_know_protocol_identity` — `trial_pipeline.py` contains no `immediate_recall`, `recognition`, or `self_confirmation`.
- `test_shared_modules_have_no_protocol_or_domain_dependencies` — shared modules do not import `hebrew`, `mantra`, `eeg`, `focuscalm`, `asr`.
- `test_two_runs_produce_identical_normalized_payloads` / `test_volatile_identifiers_are_the_only_difference` — deterministic payloads, only `session_id`/`trial_id` differ.

### 3.2 Source scan
A repository-wide search for reflection, generic dispatch, and protocol branching found:
- `importlib.metadata.version` in `mpe/cli.py` for `--version` — acceptable.
- `getattr(block, "status", None)` in `mpe/aggregates.py` — defensive, not generic dispatch.
- No `eval`, `exec`, `importlib.import_module`, `PROTOCOL_REGISTRY`, or `if protocol == ...` in shared modules.

### 3.3 Remaining duplication
- `mpe/protocol/summary.py` and `mpe/protocol/summary_recognition.py` both derive summaries from `walk_session`. They are protocol-specific summary builders over the shared walk; not duplication.
- `mpe/protocol/fixture_minimal.py` and `mpe/protocol/fixture_recognition.py` are per-fixture dataclasses; not duplication.

### 3.4 Over/under-abstraction
- **Appropriate abstraction:** `trial_pipeline.py` is a typed, generic trial runner parameterized by `InstructionSpec`, `StimulusSpec`, `ResponseWindowSpec`, `ObservationSpec`, `FeedbackSpec`.
- **Appropriate abstraction:** `bounded_repeat.py` extracts repeat mechanics while leaving repeat *decisions* to protocol code via `RepeatDecision`.
- **Appropriate abstraction:** `summary_walk.py` extracts event-order traversal; protocol-specific summaries project the walk.
- **No evidence of over-abstraction.**

### 3.5 Verdict
MPE shared layer and protocols are **architecturally sound and verified by tests**.

## 4. Curriculum audit

### 4.1 Determinism
Regenerating the curriculum twice produced different MD5s:
- `md5` run 1: `e13ec2a4b09078be14569e21d06f9204`
- `md5` run 2: `a286952258d291ddee869bf202c872d8`
- After stripping `generated_at` both normalized forms are identical.

**Finding:** The curriculum content is deterministic, but the `generated_at` timestamp in `scripts/generate_curriculum_320.py` prevents byte-identical generation. This violates the "no canonical timestamps" requirement.

### 4.2 Content issues in committed `data/hebrew/curriculum_v1_320.json`
- **320 verbs present** — verified.
- **Unique `verb_id`s: 309** (not 320). 11 plain infinitives are duplicated across binyanim (e.g., `לפנות` appears once as PA'AL `lifnot` and once as PI'EL `lefanot`). `CurriculumVerb.verb_id` is set to the plain infinitive, so it is **not a stable unique identifier**.
- **Unique `asset_id_prefix`: 320** — the Latin slug generator correctly disambiguates duplicates with counters, but the `verb_id` field does not use it.
- **Unicode normalization: 123 of 320 `infinitive_pointed` values are not NFC.** Example: `לְחַבֵּר` stores dagesh `0x5bc` before tsere `0x5b5`; canonical NFC is `לְחַבֵּר` (dagesh after vowel).

### 4.3 Audit report (`data/hebrew/curriculum_v1_320_audit.json`)
- `total_verbs`: 320
- `blocks_asset_generation`: **142** (123 `unicode_not_nfc`, 22 `duplicate_verb_id`/`duplicate_infinitive`, plus overlaps)
- This means **44% of the committed curriculum cannot be used to generate audio assets** without correction.

### 4.4 Source lookup
`scripts/audit_curriculum_320.py` builds `source_lookup` keyed by `infinitive_plain`. For duplicate infinitives (e.g., `לפנות`), the second source overwrites the first, so **one-to-many source preservation is not implemented**.

### 4.5 Severity / action monotonicity
The audit has `blocks_asset_generation` (bool), `recommended_action`, `confidence`, and `issue_categories`, but **no numeric severity scale** and no monotonic severity ordering. The `recommended_action` values (`keep`, `keep_with_note`, `correct_in_next_curriculum_version`, `exclude_in_next_curriculum_version`, `manual_review_required`) are not ordered.

### 4.6 Test fix
A local experimental fix (normalize `infinitive_pointed` to NFC, set `verb_id = unique asset_id_prefix`, and freeze `generated_at`) dropped the blocking count from 142 to **22**, and the remaining 22 were only `duplicate_infinitive` flags for legitimate homographic infinitives across binyanim.

## 7. Audio architecture audit

### 7.1 AudioProfile
- `AudioProfile` is versioned, frozen, and loads from `data/audio_profiles/production.json`.
- Production profile resolves `it` -> `Giuseppe / it-IT` and `he` -> `Aaron / he-IL`.
- `cache_key_identity` includes provider, voice, locale, text, format, sample rate, channels, rate, pitch, and `cache_key_version`.
- `_cache_key` in `mantra/phase1/tts.py` uses the same payload shape.

### 7.2 AssetContract / Inventory / Readiness / PreparationPlan / ExecutionPlan
- `AudioAssetRequirement` is typed and includes `section`, `cache_key`, `required_for_core_execution`, `human_audio_review_status`.
- `AudioAssetInventory` is read-only; `classify` and `inspect` do not mutate state.
- `VerbReadinessReport` separates `learner_execution_eligibility` and `asset_preparation_eligibility`.
- `MantraExecutionPlan` and `AssetPreparationPlan` are typed dataclasses.
- `runtime.execute_mantra_plan` executes an existing plan; it does not select verbs.

### 7.3 SpeechGen isolation
- `MantraSelectionPolicy` and `build_execution_plan` never instantiate a TTS provider.
- `runtime.execute_asset_preparation_plan` is the only Phase-4D path that calls `registry.ensure`, which may call `SpeechGenTTSProvider`.
- `runtime.execute_mantra_plan` only assembles existing WAVs.

### 7.4 Stale / hardcoded voices
**Found voice identifiers outside `AudioProfile`:**
- `mantra/generator.py:295` — legacy SSML hardcodes `<voice name="he-IL-HilaNeural">` (stale Hila voice; file is dead code).
- `mantra/domain/hebrew/specification.py:160` — docstring mentions "Aaron TTS voice" in prose.
- `scripts/build_lehitkasher_hannah_full_niqqud.py` — sets `HEBREW_VOICE = "Hannah"` and `ITALIAN_VOICE = "Giuseppe"`.
- `scripts/build_compact_mantra_lehitkasher.py` and `mantra/phase1/assets.py` `ensure_tense_markers` use `voice="Hannah"`.

**Interpretation:** `AGENTS.md` explicitly states the audio design rule for the full-niqqud diagnostic is "Hebrew voice: Hannah, fully vocalized (niqqud); source_text == tts_text." The `Hannah` usage in `build_lehitkasher_hannah_full_niqqud.py` and `build_compact_mantra_lehitkasher.py` is therefore **design-consistent for those diagnostics**, not an accidental bypass of `AudioProfile`. However, these scripts still hardcode voice identifiers instead of loading them from a profile, which is technical debt if a different diagnostic profile is ever needed. The `Hila` voice in `mantra/generator.py` is genuinely stale legacy code.

### 7.5 Cache path hardcoding
- `mantra/phase1/asset_contract.py` hardcodes `target_relative_path=f"mantra_global_tts_cache/{cache_key}.wav"` instead of using `GLOBAL_CACHE_DIR`.

### 7.6 Verdict
The **core contract is clean**, but **legacy/diagnostic builders bypass `AudioProfile` and hardcode Hannah/Hila**. This is medium-priority debt and a blocker for production consistency.
