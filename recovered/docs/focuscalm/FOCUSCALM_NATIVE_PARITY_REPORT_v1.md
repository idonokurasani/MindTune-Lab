# FocusCalm Native Parity Report v1

## Scope

This report documents the static reverse-engineering findings for the
FocusCalm EEG pipeline and defines the protocol for producing a true
native golden vector.  The Python fixtures generated by
`focuscalm_lib/generate_golden_and_hashes.py` are a *reference* from the
same source CSV, not yet a native golden vector.

## Pipeline stages (native)

```
BLE payload  --(parse_content)-->  raw_s24  --(parse_content)-->  scaled sample
                                                     |
                                                     v
                                            circular buffer this+0x80
                                                     |
                                                     v
                                          linearized window this+0x88
                                          FFT magnitude buffer this+0x90
                                                     |
                                +--------------------+--------------------+
                                |                    |
                                v                    v
                compute_attention_features      compute_meditation_features
                (169 FFT bins 4-38 Hz)          (33 moments/bands/deciles)
                                |                    |
                                v                    v
                normalize? (none observed)      normalize_features
                run_network (attention)        run_network (meditation)
                output[0] * 100                output[1] * 100
                attention_moving_average       meditation_moving_average
                execute_attention_callback     execute_meditation_callback
```

## DC-offset investigation

`parse_content` (address `0x16574`) converts each 3-byte signed big-endian
integer to a double using:

```
sample = raw_s24 * 0.040690104166666664 / 128.0
```

The divisor `128.0` is read from `device_data_create` (`this+0x10 = 0x80`).
`analyze_eeg` then copies the scaled samples into the circular buffer
`this+0x80` without high-pass filtering or baseline subtraction.
`compute_meditation_features` clips the buffer in place to `[-2000.0, 2000.0]`,
computes time moments and deciles from the clipped copy, and computes FFT
magnitudes from the unclipped copy (`this+0x88`).

**No DC-removal step was found** in any of the functions traced:
`parse_content`, `analyze_eeg`, `analyze_eeg_windows`, `compute_meditation_features`,
`get_time_window_moments`, `get_frequency_band_moments`, `percentileselect`,
or `normalize_features`.

### Implication

`meditation_normalization.json` has `mean` of feature 0 (mean of the signal)
close to `-0.056`, which means the deployed model was trained on data whose
mean was effectively zero.  A real BLE stream whose `raw_s24` baseline is far
from zero will therefore saturate the meditation output, as observed on the
provided CSV.

The possible explanations are:

1. The firmware or analog front-end is AC-coupled, and the captured
   `raw_s24` values in the CSV are not representative of what `parse_content`
   actually receives (unlikely, because the CSV values are the decoded
   payload).
2. The app sets a per-device or per-session baseline somewhere not found in
   the disassembly traced so far (no static evidence yet).
3. The model embedded in `meditation_network.json` is the one shipped with the
   library and is simply not robust to the DC offset present in this
   recording.

**Resolution requires a controlled native capture** where `this+0x80` and the
network output are logged from the same execution.

## Cadence

`should_compute_attention` (`0x43898`) and `should_compute_meditation`
(`0x43b08`) both require:

- `this+0xd8 % 2 == 0` (packet index inside the 800-sample window is even);
- the corresponding contact-state flag is non-zero.

`analyze_eeg` increments `this+0xd8` each time it copies a new packet into
`this+0x80` and resets it when `this+0xd8 * this+0x68 >= 800`.

Therefore:

- Window size: `800` samples.
- Update per packet: `samples_per_packet` samples (`this+0x68`, observed 20
  for the `fc11` stream).
- Network stride: `2 * samples_per_packet` samples (every 2 packets).
- Overlap: `800 - 2 * samples_per_packet` samples.
- For `samples_per_packet = 20` and `fs = 160.6 Hz`:
  - stride ≈ `40 / 160.6 = 0.249 s`
  - overlap ≈ `760 / 160.6 = 4.73 s`
- During packet loss the circular buffer simply skips the missing samples; the
  next copy overwrites the oldest block, and `this+0xd8` still increments.
  When `this+0xd8 * samples_per_packet >= 800` it wraps to zero, so one
  window may span non-consecutive payload indices.

## Output semantics

- **Attention network**: 169 inputs -> 3 outputs (`attention_network.json`).
  `analyze_eeg_attention` (`0x43830`) uses `output[0] * 100.0` as the raw
  attention score, then passes it through `attention_moving_average`.
- **Meditation network**: 33 inputs -> 2 outputs (`meditation_network.json`).
  `analyze_eeg_meditation` (`0x43aa0`) uses `output[1] * 100.0` as the raw
  meditation score, then passes it through `meditation_moving_average`.

## Smoothing

- `attention_moving_average` (`0x4375c`): 20-slot ring, initial value 2.5,
  accumulator initial value 50.0 (`20 * 2.5`). Each incoming score is divided
  by 20 before being added, so the steady-state output is the arithmetic mean
  of the last 20 scores.
- `meditation_moving_average` (`0x439b0`): 80-slot ring, but the value written
  20 steps ago is subtracted, so the effective window is also 20. Initial
  ring value 2.5, accumulator 50.0.

## Controlled capture protocol

To create a real golden vector the native library must be instrumented while
processing a known BLE stream.  One reliable method is Frida.

### 1. Capture target

Hook the following functions in `libfusi.so`:

- `parse_content(device_data, payload, length)`
- `analyze_eeg(device_data)`
- `compute_attention_features` / `compute_meditation_features`
- `normalize_features`
- `run_network`
- `analyze_eeg_attention` / `analyze_eeg_meditation`
- `attention_moving_average` / `meditation_moving_average`
- `should_compute_attention` / `should_compute_meditation`

### 2. Values to dump per invocation

For each `analyze_eeg` call that computes a score, record:

1. the raw BLE payload bytes (`this+0x58`, length `this+0x64`);
2. the decoded `raw_s24` values in the payload;
3. the scaled samples copied to `this+0x70`;
4. the full `this+0x80` circular buffer at the moment `analyze_eeg_windows`
   is called (800 doubles);
5. the linearized `this+0x88` window (800 doubles);
6. the FFT magnitude buffer `this+0x90` (first 200 bins);
7. `this+0xd8` (packet index), `this+0x68` (samples per packet), contact flags;
8. attention features (169 doubles from `this+0xa0`);
9. meditation features before normalization (33 doubles from `this+0xa8`);
10. meditation features after normalization (same buffer after
    `normalize_features` returns);
11. `run_network` raw output for attention (3 doubles) and meditation
    (2 doubles);
12. raw scores `output[0]*100` (attention) and `output[1]*100` (meditation);
13. smoothed scores returned by the moving averages;
14. monotonic timestamp or frame counter that proves temporal alignment.

### 3. Golden criteria

A fixture can be declared *golden* only when the same native execution
produces the BLE input and every intermediate value above, all tagged with
an unambiguous index/timestamp.

### 4. Frida capture harness

Two helper files are provided in `focuscalm_lib/`:

- `native_capture_frida.js` — Frida script that hooks the relevant `libfusi.so`
  functions by offset and sends each computed window to the host.
- `run_frida_capture.py` — host-side runner that attaches to the FocusCalm app
  (`tech.brainco.focuscalm`), collects the windows, and writes
  `native_capture.json`.

Setup:

```bash
.venv/bin/pip install frida frida-tools
adb shell /data/local/tmp/frida-server   # on a rooted/patched device
```

Run:

```bash
cd /Users/idonokurasani/focuscalm_lib
.venv/bin/python run_frida_capture.py tech.brainco.focuscalm
```

The resulting `native_capture.json` has the same schema as
`FOCUSCALM_CONTROLLED_CAPTURE_GOLDEN_v1.json` and can be compared with
`test_native_parity.py`.

### 5. Comparison

`focuscalm_lib/test_native_parity.py` reads a native capture JSON and the
reference JSON produced by `generate_golden_and_hashes.py` and compares the
values stage-by-stage within a configurable tolerance.

## Reference-run observation

Using the provided `fc11_stream_1781471387_eeg.csv` as input, every generated
window has a `features_pre_norm[0]` (mean) around `78.7`. After normalization and
the softmax meditation network, `score_raw` is essentially `100.0` for all
windows (e.g. window 0: `99.9999999512`). This confirms that the disassembly-derived
pipeline saturates on this recording because the signal mean is not removed
anywhere in the native path, exactly as predicted in the DC-offset section.
